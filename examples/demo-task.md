# 比赛演示任务：多 Agent 协作开发与自动修复系统

> 本文件是演示**说明与操作脚本**，不是执行记录。所有执行结果必须来自软件内的真实运行，
> 演示时现场执行、现场展示日志；不得使用预录文本冒充实时执行。故障注入项目会明确标注。

## 〇、前置准备（演示前完成，约 10 分钟）

1. 按主 README「快速开始」启动后端（`:8000`，`curl /health` 返回 ok）与前端（`:5173`）。
2. 在「设置」页添加至少一个真实可用的 OpenAI 兼容模型供应商，并点「测试连接 /
   拉取模型」确认能真实返回模型列表。**主任务演示依赖 LLM 生成代码，没有可用
   供应商时任务会以 MODEL_ERROR 明确失败，无法演示**——这是真实性设计，不是故障。
3. 供应商与模型就绪后，再按下文创建 Agent / 团队 / 任务。
4. 无供应商时仍可演示的部分：调度/验证/Self-Loop 引擎级闭环可由仓库
   `benchmarks/run_benchmark.py` 真实复现（不调用 LLM，见 benchmarks/README.md）；
   共享 Linux 工作区（下文第四节）不依赖 LLM，可独立演示。

## 一、演示团队（在「AI 员工」页创建 5 个 Agent）

| Agent | 角色 role | 能力标签 capability_tags | 说明 |
|---|---|---|---|
| Project Manager | planner | planning | 分析需求、生成任务 DAG |
| Software Architect | architect | research, design | 设计 API 结构与数据库模型 |
| Developer | developer | coding, general | 生成真实项目代码 |
| Test Engineer | tester | testing, review | 生成并运行 Pytest 测试 |
| Quality Reviewer | reviewer | review | 检查测试证据与需求完成情况 |

每个 Agent 在「设置」页先添加真实的 OpenAI 兼容模型供应商，创建 Agent 时从上游
`/models` 接口拉取并选择模型。未配置供应商时任务会明确失败（MODEL_ERROR）——
这是预期行为，不是演示素材。

## 二、演示任务（在「任务中心」创建并执行）

标题：开发一个用户管理 REST API

要求：
- 用户注册 / 用户登录 / 用户信息查询 / 用户信息修改 / 角色权限控制
- 技术：Python FastAPI + SQLite + Pytest

系统自动流程：规划生成 DAG → 调度器按能力画像分配 Agent（决策记录可在
「任务中心 → 调度决策」与「可信验证」页查看）→ Agent 执行 → 结构验证 →
失败进入 Self-Loop 修复 → 重新验证 → 输出结果与验证记录。

## 三、故障注入（明确说明：这是预先准备的故障注入测试项目）

准备方式（先说清 Bug 从哪来）：把一个存在**真实权限校验 Bug** 的用户管理 API
项目（普通用户可以访问管理员接口）连同其 pytest 测试放入共享工作区——通过
「共享电脑」页的文件写入，或直接拷贝到共享根目录（默认
`services/agent-core/data/shared_workspace`，逻辑路径 `/workspace`）。

演示步骤：

1. Test Engineer 在自己的终端会话中对该项目执行 pytest（工具 `run_pytest` /
   会话命令执行，均为真实子进程）→ 权限测试**真实失败**。
2. 验证引擎（工具验证层）捕获 pytest 失败输出作为证据；任务内的失败节点由
   Self-Loop 按错误分类在重试上限内重新执行（应用内修复由所配置的 LLM 完成，
   需供应商可用；执行与验证记录在「可信验证」页可查）。
3. Developer 修改权限逻辑 → Test Engineer 重新运行测试 → 验证通过。
4. 展示：任务 DAG、调度决策、终端/测试输出、失败证据、修复历史、最终验证报告。
5. 可复现对照：同一闭环（验证失败 → 按失败输出修复 → 复验通过）在
   `benchmarks/` 中有 3 个缺陷任务的引擎级实测（Self-Loop 关 0/3、开 3/3；
   该对照为规则修复、不调用 LLM，口径见 benchmarks/summary.md 的局限说明）。
   现场演示与离线数据不要混为一谈。

## 四、共享 Linux 工作区演示（「共享电脑」页，不依赖 LLM）

证明多个 Agent 共用**同一台** Linux 环境、各自持有独立终端会话：

1. 在「共享电脑」页点「载入演示团队」（调用 `POST /api/workspace/seed-demo`，
   幂等）：真实创建 产品经理 / 开发工程师 / 测试工程师 3 个 Agent 与一个团队。
2. 分别为开发工程师、测试工程师创建终端会话（两人 `env_id` 同为
   `shared-linux-1`，会话彼此独立、工作目录互不影响）。
3. 开发工程师在自己会话中向 `/workspace` 写入一个文件（如项目代码）；
   测试工程师在自己会话中**读到同一份文件**并运行其 pytest——同环境共享、
   非各自拷贝。
4. 展示文件版本/锁定、命令日志、事件流；如需桌面操作，展示桌面控制权租约
   （同一时刻只有一个会话持有，其他会话需等待或经租约流程接管）。

## 五、调度模式对比演示（可选，约 5 分钟）

1. 在「任务中心」新建任务时，调度模式可选 fixed / round_robin / adaptive
   （任务字段 `scheduler_mode`，默认 adaptive）。
2. 用同一标题与要求、同一团队分别以三种模式各建一个任务并执行。
3. 在「任务中心 → 调度决策」对比每个节点的被选 Agent、候选评分与选择原因，
   说明自适应模式与固定/轮询的差异。注意：无可用供应商时三种模式都会在
   执行层以 MODEL_ERROR 失败，但调度决策记录仍会真实落库，可只对比决策。
